# Node.js 网关内存基线（第一阶段）

日期：2026-09-26。后续状态：2026-09-27 已实施表格库按需加载与 API Runtime 资源归属，见 [实现计划](node-architecture-gap-plan.md)。下述数字仍是优化前基线，未复测。

范围：**测量与定位，尚未实施生产内存优化**。结构化结果见 [原始摘要](evidence/memory-baseline-2026-09-26.json)。

## 结论

当前完整 API 在本机、关闭请求日志和调度器的条件下，冷启动空闲末值约 **112 MiB RSS**；32 路并发普通流峰值约 **150 MiB**；8 路慢读大响应峰值约 **183 MiB**；结束后观察 30 秒，自然回落至约 **96 MiB**。回落时活动 HTTP 请求与 Undici 活动请求均为 0，JS 堆约 40 MiB，ArrayBuffer 约 0.39 MiB。

这批短负载没有出现请求持续滞留或未结算记录。不能据此证明长期无泄漏，也尚无 Python 同条件对照，不能宣称节省比例。RSS 不必回到启动时的相同数字；GC、分配器和操作系统回收都会影响它。

## 环境与方法

- Apple M5 / 10 逻辑核心 / 32 GiB，macOS arm64；Node **22.19.0**，PostgreSQL **14.20**。共享开发机，无容器 CPU/内存配额，不能据此推算生产容量。
- 源码基线 `e999b7f` 加本地职责拆分；结果记录源码（含未跟踪源码）、脚本、锁文件 SHA-256。未提交、未推送。
- **负载工具、模拟上游、网关分别独立进程**。网关运行临时编译的 JS，不使用 tsx/watch。编译和 DB 初始化在测量前完成，第二轮测量期间未并行运行构建、类型检查或测试。
- API 加载完整管理/网关路由。使用测试配置，logger=false、scheduler=false、不提供前端静态资源；不包括生产访问日志、后台 worker、数据库进程及前端开发服务器的内存。
- 500 ms 采样 RSS、heapUsed、external、arrayBuffers、CPU、事件循环延迟、活动请求、HTTP 连接和 DB 池状态；短于采样间隔的峰值可能遗漏。ArrayBuffer 属于 external 的一部分，不应相加后当作 RSS。
- 新建随机名隔离 DB，实际应用 **42 个迁移**，只放模拟模型、账号和临时 key。保留认证、有限 key 额度、并发限制、预留与结算；没有访问用户原有配置或供应商。
- 仅测试 **OpenAI Chat → OpenAI Chat 的 HTTP/SSE**。普通流 64×1 KiB、25 ms/帧；慢读流 192×32 KiB、5 ms/帧，客户端每次读取后停 100 ms。客户端增量解析，不将全部响应累积到内存。
- 上游报告固定 synthetic usage（128 输入、64 缓存、64/192 输出），用于逐次对账，**不是实际对输出字符分词得到的 Token 数**。
- 40 秒阶段固定每秒发起 4 请求，最多 8 并发，没有跳过到达。负载端和模拟上游 CPU 峰值分别约 15.3% / 17.6%（100% 为一个 CPU 核）；该负载下未见它们持续 CPU 饱和，仍不代表吞吐极限已测出。
- 网关 RSS 达 1 GiB 或总耗时达 10 分钟时终止，失败也关闭自己的进程并尝试删掉自己的库。最后额外执行一次显式 GC，单独标为诊断，**不作为自然回落的证据**。

## 网关进程测量值

单位 MiB。峰值按 500 ms 定时样本统计；导入阶段单独见下文。末值表示该阶段最后一个定时样本，不是历史最小值。

| 场景 | RSS 峰值 | RSS 末值 | JS 堆峰值 | ArrayBuffer 峰值 |
| --- | ---: | ---: | ---: | ---: |
| 冷启动后空闲 10 秒 | 141.6 | 112.3 | 47.3 | 0.3 |
| 预热：2 并发 / 8 请求 | 135.6 | 135.6 | 44.3 | 0.8 |
| 预热后空闲 5 秒 | 135.7 | 103.3 | 42.9 | 0.5 |
| 普通流：8 并发 / 24 请求 | 122.0 | 122.0 | 48.9 | 1.3 |
| 普通流：32 并发 / 96 请求 | 149.6 | 149.6 | 59.9 | 2.3 |
| 慢读：8 并发 / 每请求约 6 MiB | 182.8 | 178.9 | 55.6 | 15.6 |
| 首块后主动取消 8 次 | 179.6 | 179.6 | 50.2 | 3.9 |
| 4 请求/秒，持续 40 秒 | 179.7 | 172.8 | 60.8 | 4.8 |
| 停止负载，自然回落 30 秒 | 172.8 | 95.7 | 53.3 | 1.3 |

启动阶段另有显式快照：辅助运行时代码加载后 RSS 约 50.2 MiB / 堆 6.6 MiB，应用模块导入后 RSS 约 175.8 MiB / 堆 88.6 MiB，路由就绪后 RSS 约 141.4 MiB / 堆 47.1 MiB。这里会穿插自然 GC，**不是每个阶段净保留量的精确分解**。

首次联调得到的空闲/32 并发/慢读/自然回落约为 109.7/146.5/188.7/111.3 MiB；其部分时间与构建检查重叠，只作工具联调参考。最终复核使用上表，不挑选两轮中最好数字拼接。两次回落差异也说明不能把小幅 RSS 波动直接当优化收益。

## 正确性与清理

- **304 次请求**：296 正常完成、8 次主动取消；0 次非预期失败。
- 正常请求逐次 wire usage 与账本一致；合计输入 **37,888**、输出 **19,968**、缓存读取 **18,944**（模拟值）。
- 8 次取消均记为 `client_error`，没有收到上游最终 usage，保留 `estimated` 估算口径；不冒充供应商精确用量，不混入上述正常请求统计。
- 账本与客户端请求一一对应，**0 个 reserved**。回落后活动请求、上游活动请求和 DB 等待采样均为 0；500 ms 池采样不能排除更短的连接等待。
- 回落末尾还有 7 个来自负载客户端的空闲 keep-alive 连接，活动请求为 0。这些连接随负载工具退出关闭，不能算未释放请求。
- 子进程全部退出，随机隔离库已删除；随后查询 `pg_database` 确认没有遗留 `coati_bench_%` 数据库。

## 已定位的改进方向

### 1. 优先处理启动依赖

静态调用链中 [tabular.ts](../../apps/api/src/common/tabular.ts) 顶层导入 ExcelJS；[usage-export.ts](../../apps/api/src/modules/gateway/usage-export.ts) 顶层导入 XLSX。这意味着只做模型转发也会加载表格处理依赖。子进程 CJS 缓存探针确认 ExcelJS 已加载；该探针不枚举 ESM 模块，不能用于排除 XLSX 的加载。

分别用全新 Node 进程单独加载两个包，并在前后显式 GC 后得到：

| 单独加载实验 | RSS 增量 | 保留 JS 堆增量 |
| --- | ---: | ---: |
| ExcelJS | 29.7 MiB | 7.5 MiB |
| XLSX | 13.9 MiB | 3.0 MiB |

它们共享部分运行时/依赖，RSS 又受 GC 时机影响，**不能相加承诺节省 43.6 MiB**。下一步先将实际表格操作改为按需加载，保持 CSV/Excel 接口和权限不变，再用同一基准比较冷启动与网关负载。首次真正使用表格功能后模块仍会驻留；这是延后可选功能的加载，不是卸载模块或解决所有内存问题。

### 2. 再处理慢客户端的缓冲预算

慢读大响应使 ArrayBuffer 峰值从普通 32 并发下约 2.3 MiB 增至约 15.6 MiB。已有背压和单事件限制，但该测量还不能证明完整的实例内存上限。下一步需要核对活动请求数量、每请求缓冲、连接及排队总预算，并隔离验证后再改默认限制。

### 3. 连接池复用属于后续独立验证

现有代理路径每次创建 ProxyAgent，管理/模型服务各自持有 transport。值得整理进程资源所有权，但本轮没有 TLS/代理负载，不能将本轮数字归因于代理池，也不能宣称连接优化完成。
